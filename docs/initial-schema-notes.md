# Initial schema

**Update:** `InitialCreate` has been generated on a real machine (with the
.NET 10 SDK) and applied against a real Postgres instance — the migration
files now live in `src/Jusoor.Infrastructure/Migrations/` in this repo, so
`dotnet ef database update` on a fresh checkout no longer requires
regenerating it. The section below is kept for historical context on why
it wasn't included earlier.

## Historical note: why this wasn't generated in the assistant's sandbox

This sandbox has no .NET SDK and no network access to NuGet, so I could not
run `dotnet ef migrations add InitialCreate` to generate the real migration
files myself. Shipping hand-written EF migration/designer files without
being able to compile or apply them would risk subtly wrong metadata that
looks right and isn't — worse than not having them. The migration was
instead generated by the developer on a real machine and folded back into
this repo once confirmed working (build, all test projects, and a live
`dotnet ef database update` against Postgres via Docker Compose).

- All standard ASP.NET Identity tables (`AspNetUsers`, `AspNetRoles`,
  `AspNetUserRoles`, ...) — `ApplicationUser` adds `DisplayName` and
  `PreferredLanguage` columns to `AspNetUsers`.
- `Countries` — `NameAr`, `NameEn`, `IsoCode2` (unique), `Slug` (unique).
- `Cities` — FK to `Countries`, `NameAr`, `NameEn`, `Slug` (unique per
  country), nullable `Latitude`/`Longitude`.
- `Sources` — `Name`, `Layer` (int, spec §5's 7 layers), `ReliabilityScore`
  (decimal 3,2), `FeedUrl`, `OfficialWebsiteUrl`, `IsActive`, plus the
  `AuditableEntity` columns (`CreatedAtUtc`, `CreatedByUserId`, etc.).

## Phase 1, Slice 1 additions (news pipeline persistence foundation)

- `Stories` — `CanonicalTitle`, `Status` (int, `StoryStatus`), nullable FKs
  to `Countries`/`Cities`, `FirstSeenAtUtc`, `LastUpdatedAtUtc` (indexed —
  recency is the dominant read pattern). No embedding/vector column yet —
  see below.
- `Articles` — FK to `Sources` and nullable FK to `Stories`,
  `ExternalSourceItemId`, `CanonicalUrl`, `Title`, `ContentHash` (SHA-256
  hex, 64 chars), `DetectedLanguage`, `Status` (int,
  `ArticleProcessingStatus`), `FailureReason`. Two indexes carry the
  idempotency contract: `(SourceId, ExternalSourceItemId)` UNIQUE (protects
  against re-fetching the same feed item), and `(SourceId, ContentHash)`
  non-unique (exact-duplicate detection within one source; cross-source
  duplicates are near-duplicate clustering, a later slice).
- `RelevanceResults` — append-only audit trail, FK to `Stories` (cascade —
  meaningless without the Story) and nullable FK to the triggering
  `Article` (set-null — audit row survives article purges), `IsRelevant`,
  `ConfidenceScore` (decimal 3,2), `Method` (int, `RelevanceMethod`),
  `Reasons`, `EngineVersion`.

**Deliberately not in this migration:** a pgvector embedding column on
`Story`/`Article`. Adding an unused vector column now — before the
`Npgsql pgvector` package is wired up, tested, and something actually reads
from it — would be exactly the "tables because they look useful"
anti-pattern the engineering brief warns against. That column, plus the
near-duplicate clustering it enables, is its own slice.

## Phase 1, Slice 2 additions (SSRF-safe fetcher + RSS source worker)

- `SourceFetchLogs` — one row per ingestion attempt: `SourceId` (FK,
  cascade), `StartedAtUtc`/`CompletedAtUtc`, `Outcome` (int,
  `SourceFetchOutcome` — Success/Timeout/TransientNetworkError/HttpError/
  SecurityRejected/ResponseTooLarge/ParseError), `HttpStatusCode`,
  `ItemsFound`/`ItemsIngested`/`ItemsSkippedAsDuplicate`, `ErrorSummary`
  (safe-for-logs text only, never raw exceptions or fetched content).
  Indexed on `(SourceId, StartedAtUtc)` for "recent attempts" health
  queries.

## Phase 1, Slice 3 additions (scheduler)

No new EF-managed tables this slice. Hangfire (`Hangfire.PostgreSql`) manages
its own schema (job storage, recurring-job state, server heartbeats) in the
same Postgres database, created automatically on first connection — this is
Hangfire's own migration mechanism, entirely separate from
`dotnet ef migrations`, and intentionally not modeled in our `DbContext`.

`Program.cs` calls `Database.MigrateAsync()` automatically in the
`Development` environment on startup, so once the migration exists,
`docker compose up` applies it with no manual step — that's what the
Phase 0 "new developer running locally in under an hour" DoD depends on.

Staging/production do **not** auto-migrate on boot (see the comment in
`Program.cs`) — migrations there run as an explicit CI/CD step.
